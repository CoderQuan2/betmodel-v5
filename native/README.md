The native conversion of BetFi Xii (Pilot's decision, 2026-10-31).

Parity contract and proofs: **parity/PARITY.md**. What has actually

"BUILT" means implemented against the bridge payloads and driven
on desktop (bridge side). **Kotlin compilation is proven only by
GitHub Actions** — no JDK exists on the authoring VM.

The release build is UNSIGNED unless a `keystore.properties`
(native/ root, gitignored) supplies a keystore: release runs
minify + shrinkResources with Chaquopy keep rules either way,
and CI uploads the unsigned release APK as-is.

The Flet HTML instruments are **not** shipped in the native app:
the 3D destination is the native OpenGL ES scene (PROGRAM.md
has the axis mapping).

## How the first build runs

There is no JDK on the authoring VM, so **GitHub Actions is the
compiler** (`.github/workflows/build-native.yml` at the repo root):

1. Trigger: push touching `native/**`, or manual `workflow_dispatch`.
2. The workflow installs JDK 17 + Gradle 9.7.1 (pinned in the
   workflow — see below), runs `gradle :app:assembleDebug` and
   `gradle :app:assembleRelease` in `native/`, and uploads
   `betfi-xii-native-debug` and `betfi-xii-native-release`.
3. Install the APK on the phone beside the Flet app (distinct
   applicationId `com.betfi.xii` — it replaces nothing), open
   **Lab**, run the parity spike. Native parity closes when it
   prints **PARITY: MATCH** on the device.

## The wrapper follow-up

No `gradlew` is committed, deliberately: a Gradle wrapper jar must
be generated by a real Gradle on a real JDK, and none exists here —
a faked wrapper would be worse than none. After the first green
Actions run, generate the wrapper pinned to the proven Gradle
version (one-off Actions job or any JDK machine:
`gradle wrapper --gradle-version <proven>` in `native/`), commit
`gradlew`, `gradlew.bat`, and `gradle/wrapper/`, and switch the
workflow to `./gradlew`. Until then the workflow's pinned
`gradle-version` is the single source of the Gradle pin.

## What is unverified until Actions runs

Everything on the far side of a compiler — stated plainly:

- The version pins (AGP 9.4.1, Kotlin/Compose plugin 2.4.20,
  Compose BOM 2026.09.00, activity-compose 1.11.0,
  navigation-compose 2.9.5, Gradle 9.7.1, JDK 17) are a coherent set
  chosen from vendor compatibility notes; each carries a
  `// VERIFY at first Actions build` comment at its pin site.
  Chaquopy 17.2.0 is the one pin taken from the vendor's current
  changelog (supports AGP 9.0–9.4).
- The Chaquopy 17 KTS DSL block shape (`chaquopy { defaultConfig {
  version = "3.12" } }`) — the most likely first-build failure.
- compileSdk/targetSdk 36; raise to 37 when the runner carries the
  Android 17 platform.
- Kotlin source correctness (no compiler has seen it), the
  Chaquopy packaging of the 22 MB Python data bundle, and the
  on-device parity comparison itself.

What IS proven (desktop, this VM — see BUILD-LOG.md): the engine
copy is byte-identical; the bridge path reproduces the reference
verdicts *exactly*; the bundle data reproduces the recorded pricing
census; `bridge.init` seeds and repoints correctly.
